# HoloChat

Realtime chat built with Phoenix 1.8, LiveView, PubSub/Presence and PostgreSQL.

Phoenix, LiveView, Ecto and HEEx conventions (generated by `phx.new`) apply in full:
@AGENTS.md

This file adds the project's own rules on top. Where they are stricter, they win.

## Commands

| Task | Command |
| --- | --- |
| Dev server (http://localhost:4000) | `mix phx.server` or `iex -S mix phx.server` |
| All tests / one file / failed only | `mix test`, `mix test path/to/file_test.exs`, `mix test --failed` |
| Quality gate (run before every commit) | `mix precommit` |
| New migration | `mix ecto.gen.migration name_with_underscores`, then `mix ecto.migrate` |

`mix precommit` runs, in order: `compile --warnings-as-errors` (including Boundary checks),
`deps.unlock --unused`, `format`, `credo --strict`, `test`. Work is not done until it exits 0.

## Environment (Windows)

- Erlang/OTP and Elixir live in `C:\Program Files\Erlang OTP\bin` and `C:\Program Files\Elixir\bin`.
  In Git Bash, prefix commands with `export PATH="/c/Program Files/Erlang OTP/bin:/c/Program Files/Elixir/bin:$PATH" &&`.
- PostgreSQL 18 runs as a Windows service. Dev and test use the role `holo_chat` / `holo_chat`
  (has `CREATEDB`, not superuser). Never use or change the `postgres` superuser.
- Code reloading does not restart the supervision tree. Restart the dev server after changing
  `application.ex`, `config/*.exs` or `mix.exs`. On Windows also make sure the old `erl` process
  on port 4000 is gone.
- The compile warning `Failed to symlink node_modules folder for colocated assets: :eperm` is
  expected and harmless; ignore it.
- The repo enforces LF line endings via `.gitattributes`.

## Architecture: contexts with enforced boundaries

Boundaries are declared with the [`boundary`](https://hexdocs.pm/boundary) library and checked at
compile time. A violation is a compile warning, so it fails `mix precommit`.

```text
HoloChat.Application   top-level; deps: HoloChat, HoloChatWeb (supervision only)
HoloChatWeb            deps: HoloChat; exports Endpoint, Telemetry, Presence
HoloChat               core; exports Chat, Chat.Message
├── HoloChat.Repo      sub-boundary; private to the core
└── HoloChat.Chat      sub-boundary; deps: Repo; exports Message
```

Rules:

- **The web layer talks to the core only through context functions** (`HoloChat.Chat.*`). Never
  call `Repo`, build `Ecto.Query`s, or reach into context internals from `HoloChatWeb`. Exported
  schemas may be used as data (pattern matching, rendering, building changesets via the context).
- **One context per domain area.** A new context is a new sub-boundary:
  `use Boundary, deps: [HoloChat.Repo, ...], exports: [...]`. Then add it to the `exports` of
  `HoloChat`. Calls between contexts go through public functions and are declared in `deps`.
- **Domain side effects live in the context, next to the write.** For example, `Chat.create_message/2`
  persists and then broadcasts. LiveViews subscribe and react; they never broadcast domain events
  themselves. Presence and typing state are web-only concerns and live in `HoloChatWeb.Presence`.
- Context functions return `{:ok, value}` or `{:error, changeset | reason}` for expected failures.
  Use bang functions only where a missing record is a bug.
- Server-controlled fields (`room`, future `user_id`, ...) are set on the struct, never `cast`.
- Browser UI is LiveView. Non-browser clients will use Phoenix Channels. Both are thin adapters
  over the same context functions, and no business logic lives in either.
- Never silence Boundary in `lib/` (no `dirty_xrefs`, no `check: [in: false, out: false]`). Only
  the test support modules (`DataCase`, `ConnCase`) are exempt. If a dependency feels necessary,
  change the design or declare it explicitly in `deps`.

## Development process: outside-in TDD (mandatory)

No production code without a failing test that requires it. For every feature:

1. **Acceptance test first.** Write a LiveView test under `test/holo_chat_web/live/` that describes
   the user-visible behaviour through element IDs. Run it and confirm it fails *for the expected
   reason*, not because of a typo or compile error.
2. **Drop down a level.** When the outer test fails because the core lacks something, write a
   context test under `test/holo_chat/` for exactly that function. See it fail.
3. **Make it green with the minimum code**, then go back to the outer test. Repeat steps 2–3 until
   the acceptance test passes.
4. **Refactor** with everything green. Refactoring alone never changes behaviour or tests.
5. **Run `mix precommit`.**

Also:

- **Bug fixes start with a test that reproduces the bug.** Watch it fail, then fix.
- Never weaken or delete an assertion to make a test pass. If the test itself is wrong, say so
  and explain why before changing it.
- When reporting work, state which tests were written first and that they were seen failing.
- Tests and the code they drive go in the same commit.

## Test conventions

- Test files mirror `lib/` paths. Use `HoloChat.DataCase` for core tests and `HoloChatWeb.ConnCase`
  for web tests. Default to `async: true`.
- **PubSub and Presence are global across async tests.** Any test asserting absence, counts or
  presence must use its own room: `"name-#{System.unique_integer([:positive])}"`.
- **No `Process.sleep`.** Synchronise on real signals: `assert_receive`, `:sys.get_state/1`, or the
  `await_presence/1` pattern in `test/holo_chat_web/live/chat_presence_test.exs`. For timers, send
  the timer message directly (`send(view.pid, :typing_timeout)`) instead of waiting.
- Test data comes from plain fixture functions in `test/support/fixtures/<context>_fixtures.ex`
  (e.g. `HoloChat.ChatFixtures`), built on the context's public API. Don't use factory libraries
  or insert through `Repo` directly.
- Assert on outcomes via element IDs and `has_element?/3`, not on raw HTML or implementation details.
- Before committing new or changed async/realtime tests, run the suite repeatedly to catch flakes:
  `for i in $(seq 1 30); do mix test | grep "^Result:"; done | sort | uniq -c`.

## Test doubles: real by default, Mox at external boundaries

- Use the real thing for everything we own: Repo (SQL sandbox), PubSub, Presence, other contexts.
  **Never mock our own modules.**
- External services (third-party HTTP APIs, email or SMS providers, ...) sit behind a behaviour
  owned by the context that uses them. Each gets a real adapter and a `Mox` mock in tests, selected
  via application config. Add `{:mox, "~> 1.2", only: :test}` with the first such integration.
  Adapters built on `Req` test their HTTP layer with `Req.Test` stubs.
- Time and randomness are parameters, not mocks: e.g. `now \\ DateTime.utc_now()`.

## Code quality

- Credo runs with `--strict` using `.credo.exs`. Fix findings instead of disabling them. An inline
  `# credo:disable-for-next-line` needs a comment explaining why.
- After deleting or renaming files, Boundary can keep reporting stale warnings. `mix compile --force`
  clears them.
- New dependencies need a reason. Prefer what is already included (`Req` for HTTP, standard
  library for dates and times).

## Git

- Small, focused commits with an imperative subject line. Commit only when asked.
- `mix precommit` must pass before every commit.
